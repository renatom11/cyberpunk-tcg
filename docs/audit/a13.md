Clause 2's `CardType.UNIT` test is narrower than the printed word "Unit". A Legend that has GONE

card everywhere else: `GameState.units()` (`core/state.py:201-205`) returns field instances of any
type but Gear, so a field Legend is a Unit for attack targeting, for fights, and for every card in
the pool that reads `c.units()`. Only this trigger asks the *card type*.

**Rulings checked:**

- **015** — "A `GO SOLO` Legend on the field … **Not spendable (it is a Unit now)**; its slot sits
  empty…" (Uncertain). The Uncertain part is slot vacation and Eddie-spendability; the parenthesis
  "it is a Unit now" is the premise the whole row rests on, and it is what this finding uses. The
  trap list presumes D for *GO SOLO slot vacation* — this finding does not touch the slot.
- **027** — "Can a spent Legend use GO SOLO? … It enters the field … the keyword still lets it
  attack that turn" (Settled, CR 4.5). GO SOLO reads "pay this Legend's cost to **play it as a
  ready Unit**".
- **032** — "Does a Legend's `PLAY` trigger when it GOES SOLO? **Yes**" (Settled). A Legend played
  to the field is treated as an ordinary played Unit for triggers.
- **034** — "What happens to a Legend that leaves the field…? **Removed from the game** … DEFEATED
  triggers still resolve, after the removal" (Settled, CR 4.4). So the defeat of a field Legend is
  a real defeat that still fires triggers; the event is dispatched (`core/ops.py:459`) either way.

**Counter-case considered and rejected:** dying-night-vs-pistol ("if this Unit is named V") and
zetatech-faceplate ("When this **Unit or Legend** is spent") show the set distinguishing a Legend in
the *Legends area* from a Unit. That distinction is about the Legends area, not the field. River
Ward's trigger has no such qualifier and a field Legend is not in the Legends area.

**Internal inconsistency, same batch:** Evelyn Parker's "friendly CORPO or GANGER **Unit** steals"
(wnc.py 1248, 39 lines below) applies **no** type test at all, so a GONE-SOLO CORPO Legend does fire
it. The two scripts in the same file answer the same question in opposite directions; the card text
is identical in form.

### AUD-kerry-eurodyne-axe-attitude-audience-1 — class A (genuine ambiguity; both readings given)

**Card:** kerry-eurodyne-axe-attitude-audience (wnc.json #37)
**Clause:** "When you roll in a Gig from your fixer area, you may ignore the result and reroll it
once." / "When you roll a min or max value on a Gig, draw 1. If it's a d20, draw 3 instead."

#### Leg B — clause map

| # | Clause | Implementation |
|---|---|---|
| 1 | "When you roll in a Gig from your fixer area," | wnc.py 1221-1222 — `e[0] != "gig_rolled" or e[1] != c.player: return`. `("gig_rolled", …)` is dispatched only by `ops.gain_gig` (`core/ops.py:464-471`), which is exactly "roll in from the fixer area". Correct. |
| 2 | "you may ignore the result and reroll it once." | wnc.py 1239 + 1231-1234 — `c.maybe(reroll, …)` → `ops.reroll_gig(c2.s, c2.player, idx)`. The reroll itself is correct and happens at most once (`reroll_gig` dispatches no new `gig_rolled`). |
| 3 | "When you roll a min or max value on a Gig, draw 1." | wnc.py 1226-1229 (`after`): `v == 1 or v == sides` → `c2.draw(1)`. |
| 4 | "If it's a d20, draw 3 instead." | wnc.py 1229 `c2.draw(3 if sides == 20 else 1)`. Correct. |
| 5 | *(script → text)* "if declined, the original roll stands: check min/max on it" — wnc.py 1241 `c.later(lambda c2: after(c2) if not c2.s.has_mod("rerolled", c2.inst) else None)` | **the guard is dead in two ways.** `"rerolled"` is set nowhere in `src/` (`grep -rn rerolled src/` returns only this line), so the condition is always true; and `EffectCtx.later` pushes a `HookStep` while `EffectCtx.ask` *also* pushes an `AskStep` (`core/ops.py:167-169`) onto the same LIFO stack — the `later` was queued second, so it runs **before** the reroll question is even asked. The min/max check on the pre-reroll value therefore always happens, and `reroll` runs `after` a second time (wnc.py 1234) on the post-reroll value. |

Observed behaviour (probe, d6, `s.rng` scripted):

| roll → reroll | draws | "ignore" reading | "every roll" reading |
|---|---|---|---|
| 1 → (declined) | 1 | 1 ✓ | 1 ✓ |
| 1 → 3 | 1 | **0** ✗ | 1 ✓ |
| 6 → 3 | 1 | **0** ✗ | 1 ✓ |
| 1 → 1 | 2 | **1** ✗ | 2 ✓ |

**The two readings.**

1. *"Ignore the result" is literal* — the rerolled-away face never becomes the Gig's value, so it
   never was "a min or max value **on a Gig**", and only the surviving face can pay clause 3. Under
   this reading the script pays for a result the card told you to discard, and pays twice when both
   faces are extreme. This is also what the script's own author intended: the comment on line 1241
   says so, and line 1241 exists solely to suppress the first payout — it just never fires.
2. *Clause 3 triggers on the act of rolling* — you did roll a 1, so you draw, and the reroll is a
   second roll that can draw again. Under this reading the script is exactly right, and line 1241's
   dead guard is harmless dead code.

I lean to reading 1 (the words "ignore the result" have to do some work, and clause 3 says "on a
Gig", which names the die's standing value rather than the act), and the test is written to it. But
reading 2 is defensible on the face of the card, so this is filed as class A rather than B3. **Do
not land a fix on this one without a text ruling**; what is not in doubt either way is that the
`has_mod("rerolled", …)` guard on line 1241 is dead code that cannot do what its comment claims.

**Rulings checked:** 005 (stolen dice are not rerolled — a different question, and it confirms the
engine only rerolls where a card says to), 037 (adjust/set failures — not engaged: a reroll is not
an adjust and is not face-constrained), 039 (Start Phase order: roll in a Gig comes last, so the
reroll question lands inside the start phase — matches where the test provokes it). No ruling covers
whether an ignored roll pays out a roll-triggered effect.

## Unproven

### U-UNREACHABLE — Kerry's reroll is offered once per **turn**, not once per roll-in

wnc.py 1235-1238 guards the offer with `(c.inst, "reroll_offer") in c.s.used`, and `s.used` is
cleared by `EndTurnCleanupStep` (`core/steps.py:181`) — so the guard is per turn. The printed
"reroll it once" attaches to the *roll* ("you may ignore the result and reroll it **once**"), so a
second roll-in in the same turn should get its own offer. No legal game reaches a second roll-in:
`gain_gig` is called from exactly two places (`core/steps.py:135` in `GainGigStep`, and
`core/engine.py:138` resolving the `GIG_DIE` menu that same step opened), both once per start
phase, and no card in `data/cards/*.json` rolls in an extra Gig. I could only provoke it by calling
`ops.gain_gig` twice by hand, which no rules sequence does. Recorded, not claimed.

### N-NOTE — two abilities in this batch have no `legal=` predicate, so they can be paid for nothing

`river-ward-detective-on-the-hunt`'s Gear ability (wnc.py 1214) and `padre-man-of-the-cross`'s
set-Gig ability (wnc.py 1171) are offered on the main menu whatever the board looks like. Activating
River Ward with no cost-2-or-less Gear in hand, or Padre when one side has no Gigs, spends the
Legend and resolves to nothing (`c.choose` with an empty candidate list and no `otherwise` returns
silently). Two other Legends a few lines away do guard themselves — Hanako
(`legal=lambda c: bool(c.gigs()) and bool(c.gigs(c.rival))`, wnc.py 1267) and Panam
(`legal=…`, wnc.py 1286). This is a playability/menu-hygiene difference, not a printed-text
discrepancy — neither card's text promises the ability is unavailable — so it is a note, not a
finding.

### N-NOTE — "Reveal up to 2 Gears" (Viktor) is modelled as a private search

`EffectCtx.search_top` declares `revealed=tuple(cards)` (effects.py:276-277), which marks the five
cards as seen **by the searcher**, per that parameter's documented meaning ("the instances this
question has *shown* to the chooser"). Viktor's text says "**Reveal** up to 2 Gears … and add them
to your hand", which in TCG usage means shown to the opponent. There is no `revealed_to_opponent`
channel in `core/view` to express that, so I cannot write a test that distinguishes the two, and the
distinction has no mechanical consequence in this engine (nothing reads the rival's knowledge of a
specific card). Style/information-model note only.

## Clean

Checked clause by clause against `data/cards/wnc.json`, `docs/rules.md` and all 41 rulings; each was
also exercised on a board (probe script, plus the existing tests named below) before being cleared.

- **v-streetkid** — "CALL: Trash 3. Then, add 1 BRAINDANCE Program from your trash to your hand."
  wnc.py 1135-1139: `c.trash_top(3)` takes from the top and preserves order (ruling 022), then the
  candidate list is the **whole** trash filtered to `PROGRAM` + tag `BRAINDANCE`, evaluated after
  the trash — so a Braindance among the three just trashed is eligible, which "from your trash" is.
  The add is mandatory, matching "add 1". Probed: deck top-3 trashed, the trash's only Braindance
  auto-added to hand. `GO SOLO` is a JSON keyword, engine-handled (rulings 027, 032, 033).
- **wakako-okada-peace-and-harmony** — CALL modal is a mandatory 2-option `choose_one` (wnc.py
  1145-1146); "rival Unit -2 power this turn" uses `c.rival_units()` and a this-turn `temp_power`
  (probed: psycho-squad 6 → 4); "⊡: Decrease a Gig by up to 2" offers −1/−2 on **either** player's
  Gigs plus a decline (5 options on a one-die-each board), which is right for an unqualified "a Gig"
  and for "up to" (ruling 037).
- **dexter-deshawn-off-the-grid** — mirror image of Wakako and correct in the same places: "+2
  power this turn" targets `c.units()` (friendly field Units only — a face-up Legend in the Legends
  area is not a Unit), and "Increase a Gig by up to 2" offers +1/+2 on either side plus a decline.
- **padre-man-of-the-cross** — "Spend a rival Unit" is `spend_one(c, c.rival_units())` (wnc.py
  1169-1170); "⊡: Set a player's Gig to the same value as another player's Gig" (wnc.py 1162-1167) picks
  the target over **both** players' Gigs and then forces the source to the *other* player
  (`[(1 - o, j) …]`), which is what "another player's" means at two players. Probed: my (6,3) set to
  the rival's 5 → (6,5). Off-face targets fail per ruling 037 in `ops.set_gig`, correctly leaving
  the die alone rather than clamping.
- **viktor-vektor-sit-down-and-relax** — "Search the top 5 … Reveal up to 2 Gears with cost 2 or
  less and add them to your hand. Bottom-deck the rest in a random order." wnc.py 1186-1187:
  `search_top(5, GEAR ∧ cost ≤ 2, lo=0, hi=2, bottom_random=True)` — `lo=0` is "up to", the
  predicate is evaluated eagerly (so the ctx it closes over is safe), and *every* unpicked card of
  the five goes back, not only the Gears. Covered and passing:
  `tests/cards/test_uncovered.py::test_viktor_vektor_calls_up_two_cheap_gears_out_of_the_top_five`.
  See the second N-NOTE for the "reveal" wording.
- **dum-dum-maelstrom-triggerman** — "CALL: You may defeat a friendly Gear. If you do, draw 2.
  Otherwise, draw 1." wnc.py 1192-1194: candidates are `c.all_gear()` (own FIELD + LEGENDS, Gear
  only), `optional=True` with `otherwise=draw 1`, and an empty board runs `otherwise` immediately —
  so the no-Gear case still draws 1. Probed: no Gear → hand 1; Gear → Gear to trash and hand 2.
  "QUICK 1 €$, ⊡: +1 power this turn for each of its equipped Gear" is `Ability(cost=1,
  self_spend=True, quick=True)` with `temp_power(u, len(c2.gear(u)))` — probed on a two-Gear
  psycho-squad: 9 → 11. The `defeat` cannot be stolen by a replacement here: the pool's only two
  `would_defeat` hooks (deadman-transmitter, jackie-welles-mamas-favorite) fire on a *host*/Unit,
